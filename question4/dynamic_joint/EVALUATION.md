# 动态联合方案的配对验证约定

全部结果来自本地合成模拟器。每个策略接收的只有 `command(kind, position, channel)` 公开接口；场景真值只在执行器、完成评分、物理审计和离线回放中使用。不会连接官方演练或正式服务。

## 主指标与失败

每场主指标为该场完整任务总时间除以实际源数，再对场景等权平均。总时间包括移动（5 m/s）、测量（5 s）、切频（1 s）和真实光学清除（成功5 s，失败3 s）。另外报告总时间之和/总源数的 pooled 指标、P90、最差场景和各费用、阶段、跨源动作的分解。

任何异常、动作预算耗尽、仍有真源未清除或者费用不一致均算失败。该场 `per_source_s=null`，已花费时间另存 `elapsed_per_source_s`；存在失败的配置，其全组平均、P90、最差和pooled主指标均为null。成功子集均值只作为诊断字段，不能用来给不完整策略排名。配对差异也明确标记完整对数和失败对数。

旧联合基线固定加载 `question4/full_mission/outputs/frozen_parameters.json` 的 `parameters.joint`，禁止通过新参数文件覆盖。新参数先在开发场景确定，再冻结到独立验证。正式比较使用新种子，不用上一版坏案例选参。

## 可复现入口

参数文件格式：

```json
{
  "old_joint": {"policy": "old_joint"},
  "dynamic_joint": {
    "policy": "dynamic",
    "parameters": {"cross_source_weight": 1.0}
  }
}
```

可使用当前 `Parameters` 的任意字段；所有默认值在任务派发前展开保存。若做消融，必须确认参数确实关掉相应机制，并使用准确标签。

```powershell
.\.venv\Scripts\python.exe -X utf8 -m question4.dynamic_joint.evaluate --stage develop --variants question4/dynamic_joint/variants.json --seed-start 20285000 --count 16 --workers 6
.\.venv\Scripts\python.exe -X utf8 -m question4.dynamic_joint.evaluate --stage validate --count 100 --workers 6
.\.venv\Scripts\python.exe -X utf8 -m question4.dynamic_joint.audit
.\.venv\Scripts\python.exe -X utf8 -m question4.dynamic_joint.evaluate --stage replays --workers 6
```

`--output` 可指定独立批次目录。`--freeze-from 配置名` 只能在完整成功的develop结束后使用；它保存旧基线和所选新配置。也可以明确保存多组冻结配置用于消融。不会仅凭开发均值自动把参数变更成默认策略。

非连续开发回归可用 `--seeds 20286088,20286096`。保留旧实现后，可用 `audit --policy-archive .../policy_source` 核验旧源码哈希；这不会绕过动作、物理或完成状态检查。

## 证据和完整性

- 每场gzip日志保存完整命令、实际反馈、费用、各频道发现/清除时刻及评估真值。
- 每个未知频道保留自己的真实负观测和连续覆盖证明支持点。计划中的点不算观测，网格剩余质量为零不算无源。
- 独立审计从真值与动作重新计算180°接收、半径、示向度误差、20m清除、切频状态、五类费用、阶段和每源账本。
- 已认证的无源频道必须用实际测到的负观测支持，通过连续覆盖几何的再次验证。允许保留早先有效证明子集，避免新增点改变Delaunay对角线后误丢证书。
- 同seed所有策略必须使用同一场景。执行码哈希在批次前后核对，运行中修改策略不能当成冻结成绩。
- 配对95%区间用5000次场景级bootstrap，随机种子419；差值为first−second，负值表示first更快。
- 详细回放重新执行所选坏案例，最终时间、动作数和完成状态必须和原基准一致。

规划CPU墙钟时间单独报告，不混进题目定义的虚拟运动/操作时间。时间估计、离散概率积分和有限候选选点仍是近似；本工具不会把它们当作精确全局最优解。

## 开发烟雾检查

20285000属于开发场景。`harness_check`的旧基线实跑为14/14清除，6441.7506428 s、460.1250459 s/源、317条命令；独立审计通过。`first_smoke`和`current_smoke`属于开发中早期版本，已保存真实动作和费用，分别1084.0079134和1140.7749965 s/源，明显退步；不能当成最终动态算法或冻结验证成绩。两次测试之间修正了连续证明支持坐标取整问题，保留历史而不覆盖。

## 开发、失败记录与重新冻结

8场×7设置开发（种子20285000–20285007）均完成，56任务共22954动作独立审计通过。所选cap60/f1为489.0206 s/源，旧基线496.5962；仅这8场的配对95%区间跨0，不能认定稳定提速。

首次100场验证（20286000–20286099）旧基线100/100，新方案98/100。88和96两场因共享/细化候选绕过单源射频步数门槛，反复失联，最终触发500移动预算。新方案完整均值为null，未把未完成任务的短时间算入成绩。该组统计、日志、失败审计、参数和当时源码完整保存于`outputs/pre_budget_fix`；逐场histories仍在原位置，避免破坏原绝对引用。

修复将同一个射频资格门槛用于所有全局候选、跨源价值和停点补测。88/96转为明确的开发回归样本，分别525.8783/686.8240 s/源、均真实清除完成；25源688动作独立审计通过。所选参数未改。修复后的独立验证改用全新种子20288000–20288099，不将回归成绩插回前次98/100冒充首次冻结全过。

新100场最终均完整清除：每个策略1234/1234源。旧联合534.5745，新动态524.3694 s/源；新−旧配对差−10.2051 s/源，95%bootstrap区间[−18.6521,−2.0948]，61/100场新方案更快。P90为668.7982→637.1765，最差为775.8435→722.4902。两策略200任务64435条实际动作独立审计全部通过；本组没有失败或重复测点，执行码前后哈希一致。

前次98/100失败组仍然保留。新的100场结果不能覆盖它的历史，也不代表任意场景必然提速；参数/实现仍有启发式近似和显式动作预算。详细数据以主`outputs/validate.json`及`outputs/audit.json`为准。
